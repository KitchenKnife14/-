## Результаты

### P1 — LOCK-01: глобальная блокировка всё ещё действует

Файл, строки 47–85, `doPost(e)`:
- каждый `telegramWebhook` получает `LockService.getScriptLock()` и ждёт до 20 секунд;
- все остальные POST-действия также получают тот же ScriptLock и ждут до 20 секунд;
- блокировка удерживается на всём протяжении обработки запроса;
- под ней находятся не только изменения, но и обычные чтения, включая `query/select`, `getSession`, `getUser`, read-only RPC;
- `signup`/`signin` также выполняют PBKDF2 внутри общей критической секции.

Это подтверждает исходную критическую находку. В загруженной копии нет `requestLockMode_()`; в ветке `ispravleniya` helper есть, но он не подключён к `doPost`. Значит, в обоих вариантах глобальная блокировка пока не устранена.

### P1 — Telegram: неизвестный тип операции по умолчанию становится расходом

Строки 983–984:
- `isIncome` распознаёт ряд слов дохода;
- всё, что не распознано как доход, получает `kind='expense'`;
- явного распознавания перевода и безопасного отказа для неоднозначного текста нет.

Следствие: фраза вроде «Перевод 500 рублей» может быть записана как расход. Это остаётся открытым TG-01 и требует блокирующего теста. Нельзя считать парсер безопасным только потому, что распознаются доходы и расширен список категорий.

### P1/P2 — Telegram: сохранение операции и update_id не атомарны

Строки 1032 и 1036:
- сначала создаётся транзакция через `query_(... mode:'insert')`;
- только после успешного возврата сохраняется `telegram:update:<id>` в ScriptProperties.

Если процесс завершится после записи строки операции, но до сохранения update_id, повторная доставка Telegram может создать вторую операцию. ScriptLock предотвращает одновременную обработку, но не устраняет это окно сбоя. Это известный TG-04; требуется отдельный тест и решение об идемпотентности на уровне операции.

### P2 — Telegram parser: расширение категорий не решает неоднозначность

Строки 989–1027:
- расширен набор алиасов доходов и расходов;
- добавлена нормализация регистра, «ё/е» и пунктуации;
- категория по умолчанию — «Прочие доходы» или «Неопределённая категория», если такая категория найдена.

Ограничения:
- алиасы — эвристики, не полноценная классификация;
- любое неизвестное сообщение с одной суммой всё ещё становится расходом;
- «перевод» не выделен в отдельный тип;
- regex `/то\b/i` в алиасе обслуживания автомобиля использует ASCII-семантику границы слова JavaScript; для кириллического «ТО» такой шаблон не является надёжным совпадением. Это локальный дефект алиаса, не основание для ошибочной записи само по себе.
- если категория по умолчанию отсутствует/архивирована, `category_id` может остаться пустым; серверная валидация допускает это.

### P2 — денежная валидация неполная

Функция `validateRelations_()`, строки 437–479:
- для `transactions.amount_kopecks`, `goal_contributions.amount_kopecks`, `recurring_payments.amount_kopecks` и `accounts.starting_balance_kopecks` применяется `Number(...)`;
- числовые строки могут пройти проверку, хотя контракт приложения — целое число копеек;
- поля `planned_purchases.estimated_kopecks`, `goals.target_kopecks`, `budgets.limit_kopecks`, `monthly_plans.planned_kopecks` не получают единой проверки в этой функции;
- отдельный RPC `create_goal_with_purchase` проверяет target, но это не закрывает прямые CRUD/upsert/batch пути для остальных полей.

Это подтверждает FC-01/FC-02. Нужна единая проверка во всех путях записи; исправлять без регрессионных тестов нельзя.

### P2 — side effects на путях чтения мешают безопасно снять lock

- `sheet_()` (строки 96–118) создаёт отсутствующий лист, записывает заголовки и форматирует лист; при несовпадающем заголовке может дописывать недостающие конечные столбцы.
- `authSheet_()` (строки 202–205) создаёт скрытый `_auth`, если его нет.
- `requireUser_()` (строки 366–372) вызывает `authRows_()`, а тот вызывает `authSheet_()`; также удаляет просроченную сессию из ScriptProperties.
- следовательно, классификация `query/select`, `getSession` и `getUser` как «read-only» без предварительного изменения этих путей небезопасна.
- `get_table_revision`, `get_telegram_link_status`, `get_my_context` читают данные, но сначала проходят авторизацию через `requireUser_()`, у которой есть перечисленные побочные эффекты.

Это подтверждает, почему `requestLockMode_()` нельзя просто подключить к `doPost` в текущем состоянии.

### P2 — аутентификация и стоимость критической секции

- `signup_()` создаёт PBKDF2-хеш внутри общего ScriptLock.
- `signin_()` проверяет пароль и для неизвестного email вычисляет dummy PBKDF2 внутри общего ScriptLock.
- `pruneSessions_()` перебирает все ScriptProperties при каждом signup/signin.
- PBKDF2 реализация прошла независимую проверку тест-векторов, но текущие 30 000 итераций ниже ориентира OWASP для PBKDF2-HMAC-SHA256. Это отдельный security/performance вопрос; повышать число итераций без оценки времени и миграционного плана нельзя.

### P2 — ручной selfTest может удалить одноимённый лист

Функция `selfTest()`, строки 1062–1077:
- до теста удаляет уже существующий лист с именем `_selftest_tmp`;
- затем создаёт одноимённый временный лист и удаляет его в `finally`.

Если в привязанной таблице уже есть пользовательский лист с таким именем, запуск selfTest удалит его. **Не запускать selfTest в основной таблице.** Для будущей тестовой версии следует использовать уникальное имя и отказываться удалять ранее существовавший лист.

### P2 — прочие подтверждённые ограничения

- `writeRows_()` очищает содержимое строк ниже нового массива данных. В загруженной копии не найдено вызовов этой функции за пределами её объявления; это потенциально опасный helper, но текущий аудит не подтверждает активный путь потери данных.
- `query_` при удалении категории не проверяет все ссылки из операций, бюджетов, регулярных платежей, планов и покупок; остаётся FC-06.
- `syncGoalTotals_()` суммирует через Number без проверки безопасного диапазона результата; связан с FC-13/денежной целостностью.
- составные RPC (например, создание цели с покупкой, подтверждение покупки/регулярного платежа) выполняют несколько операций записи без транзакции Google Sheets. Есть ручные компенсации в отдельных местах, но общей атомарности нет.
- глобальная ScriptLock сейчас сериализует эти составные операции, однако после его разделения нельзя допускать race conditions между ними.

## Следующие действия по LOCK-01

1. Зафиксировать baseline по `lockMs`, `workMs`, `totalMs` в отдельном тестовом Apps Script проекте/таблице; измерить p50/p95 для чтений, записей, signin и webhook.
2. Разделить операции на чистые чтения, обычные записи, составные записи, auth/session mutations и Telegram idempotency.
3. Убрать schema creation/repair из request-time read paths: отдельная проверка структуры/инициализация до запуска API; read path должен завершаться ошибкой, а не создавать листы/заголовки.
4. Спроектировать авторизацию для read path без записи просроченной сессии; очистку просроченных ключей выполнять отдельно.
5. Оставить атомарные секции для signup uniqueness, family membership, row writes, mixed batch, recurring/purchase confirmation и Telegram update handling.
6. Только после этого подключать классификатор; batch с любой записью — целиком write; неизвестный action — fail-closed.
7. Добавить конкурентные тесты и проверить на изолированной тестовой таблице.
8. Не публиковать этот вариант в Production и не направлять тестовый скрипт на основную таблицу.
