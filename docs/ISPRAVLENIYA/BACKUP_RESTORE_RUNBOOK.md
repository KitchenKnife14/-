# Резервное копирование и восстановление — безопасный runbook

Статус: проект процедуры. Автоматическое резервирование и проверенное восстановление пока не реализованы.

## 1. Границы и запреты

- Все пробные действия выполнять только на отдельной тестовой Google-таблице и тестовом Apps Script.
- Не восстанавливать данные поверх исходной таблицы. Восстановление выполняется в новую отдельную копию.
- Не открывать доступ к резервной таблице по ссылке и не добавлять лишних редакторов.
- Не помещать в Git, этот документ, логи или обычные текстовые архивы значения паролей, password hashes, session tokens, Telegram-токены, webhook secrets или другие секреты.
- Не запускать тест восстановления на рабочей таблице. Не менять Production deployment, основной Apps Script или действующий Telegram webhook.
- До первого теста сверить ID исходной и целевой таблицы визуально в адресной строке. Если есть сомнение — остановиться.

## 2. Что входит в состояние приложения

### 2.1. Данные Google Sheets

Текущая схема из `TABLES` в `google-apps-script/Code.gs`:

- `profiles`
- `families`
- `family_members`
- `categories`
- `accounts`
- `transactions`
- `recurring_payments`
- `budgets`
- `goals`
- `goal_contributions`
- `planned_purchases`
- `monthly_plans`
- `notifications`
- `telegram_links`
- `telegram_link_codes`

Дополнительно существует скрытый лист `_auth` с email, солью и хешем пароля. Его нужно сохранить для восстановления входа, но он содержит чувствительные данные и должен оставаться закрытым. Не раскрывать лист и не копировать его содержимое в отдельные файлы.

Копия Google Sheets должна содержать все перечисленные листы и `_auth`, включая заголовки, строки, скрытое состояние и форматирование. CSV из отчётов не является полной копией.

### 2.2. Исходный код и конфигурация

Хранятся отдельно от таблицы:
- исходники Apps Script и `appsscript.json` в Git, ветка `ispravleniya`;
- настройки Apps Script deployment (URL, версия, execute-as, access);
- OAuth scopes и выданные разрешения;
- настройки Preview/Production Vercel;
- настройки Telegram webhook и токен бота.

Копия Spreadsheet сама по себе не доказывает, что связанный Apps Script, его свойства и deployment восстановлены. После создания копии необходимо открыть Extensions → Apps Script и отдельно проверить, какой проект связан с копией. Не предполагать, что копирование таблицы корректно скопировало/перенастроило скрипт.

### 2.3. Script Properties

По текущему `Code.gs` обнаружены следующие ключи и пространства имён:

| Ключ / шаблон | Назначение | Как обращаться при восстановлении |
|---|---|---|
| `TELEGRAM_BACKEND_SECRET` | Секрет внутренней проверки Telegram webhook | Повторно задать безопасным способом в свойствах тестового Apps Script; не записывать значение в Git |
| `SIGNUP_DISABLED` | Флаг закрытой регистрации | Проверить вручную; при необходимости задать `1`, иначе удалить |
| `DEBUG_INFO` | Включает имя таблицы в GET-ответе | Должен быть удалён/выключен на публичном deployment |
| `session:*` | Временные сессии пользователей | Не переносить; после восстановления пользователи входят заново |
| `loginfail:*` | Временные счётчики неудачных входов | Не переносить |
| `table_revision:v2:*` | Маркеры ревизий для клиентского кэша | Не переносить; после восстановления кэш должен считаться новым |
| `telegram:update:*` | Кэш обработанных Telegram updates | Не переносить |
| `telegram:last_prune` | Время последней очистки update-кэша | Не переносить |

Это инвентаризация по текущему исходному коду, а не снимок реальных свойств live-проекта. Перед восстановлением проверить фактический список ключей в соответствующем Apps Script проекте, не раскрывая значения.

Токен Telegram Bot API обычно задаётся отдельно в среде Vercel/в настройках webhook-интеграции; его наличие и точное место хранения проверять по конфигурации окружения, не печатая значение.

## 3. Ручное создание резервной копии (тестовая среда)

1. Открыть именно тестовую Google-таблицу. Сверить её название и URL/ID с тестовой конфигурацией.
2. Убедиться, что таблица приватная и доступна только необходимым аккаунтам.
3. Выбрать **Файл → Создать копию**.
4. Назвать копию с датой и временем, например `TEST-budget-backup-YYYY-MM-DD-HHmm`. Сохранить её в закрытой папке Google Drive.
5. Открыть созданную копию и проверить наличие всех 15 прикладных листов и скрытого `_auth`. Сверить заголовки с `TABLES` и заголовки `_auth`: `id,email,salt,password_hash,display_name,created_at`.
6. Сверить число непустых строк в каждом листе между источником и копией. Не публиковать и не переносить эти данные в журнал; фиксировать только факт совпадения.
7. Убедиться, что копия не получила более широкие права доступа, чем исходная таблица.
8. Зафиксировать имя файла, дату/время, владельца и факт проверок в закрытом операционном журнале. Не записывать в Git ID таблицы, если репозиторий публичный, и не записывать данные строк.

Если какой-либо лист отсутствует, заголовки отличаются или права доступа расширились — считать копию непроверенной и не использовать её для восстановления.

## 4. Пробное восстановление (только в новую тестовую копию)

1. Выбрать проверенную резервную копию тестовой таблицы.
2. Через **Файл → Создать копию** создать ещё одну новую таблицу для восстановления. Не использовать исходную таблицу и не перезаписывать резервную копию.
3. Проверить все листы и заголовки по разделу 2.1, включая скрытый `_auth`. Проверить количества строк без публикации значений.
4. Открыть Apps Script из новой таблицы. Проверить привязку проекта; если проект отсутствует или связан с другой таблицей, создать/подключить отдельный тестовый проект и загрузить проверенные исходники из ветки `ispravleniya`. Не подключать этот проект к основной таблице.
5. Проверить manifest: `Europe/Moscow`, V8. Отдельно проверить фактические project timezone и spreadsheet timezone. Manifest в Git не подтверждает фактические настройки проекта.
6. Настроить только необходимые тестовые Script Properties. Секрет `TELEGRAM_BACKEND_SECRET` должен быть отдельным тестовым значением; не использовать production secret. Удалить/не создавать `DEBUG_INFO`. Проверить желаемое состояние `SIGNUP_DISABLED`.
7. Не переносить transient keys `session:*`, `loginfail:*`, `table_revision:v2:*`, `telegram:update:*`, `telegram:last_prune`. Считать, что пользователям потребуется повторный вход, а кэш будет построен заново.
8. Создать отдельное тестовое web-app deployment. Не менять существующий Production deployment и не менять рабочий Telegram webhook. Если требуется проверить Telegram, использовать отдельный тестовый бот и отдельный тестовый webhook.
9. Проверить API health/version без включения `DEBUG_INFO`. Проверить вход тестового пользователя, чтение нескольких тестовых записей и сохранность связей между семьёй, участниками, счетами, категориями и операциями.
10. На тестовых данных выполнить одну безопасную запись, затем повторно прочитать её. Проверить, что суммы остаются целыми копейками, даты корректны, а второй тестовый участник видит ожидаемые семейные данные.
11. Зафиксировать результат и удалить тестовые данные/окружение только после сохранения доказательств теста и отдельного решения. Не удалять исходную таблицу или резервную копию.

Успех копирования файла не равен успешному восстановлению. FC-12 можно закрывать только после прохождения всего теста на отдельной копии.

## 5. Что не автоматизировать до отдельного решения

Автоматический backup через `DriveApp` потребует:
- выбранной закрытой папки Google Drive и проверки владельца/прав;
- согласованного расписания и срока хранения (retention);
- проверки квот Google Apps Script/Drive и обработки ошибок;
- явного OAuth scope и повторной авторизации тестового проекта;
- проверки, что копии создаются в ожидаемом месте и остаются приватными;
- мониторинга успешности и оповещения о пропущенном backup;
- защиты от параллельного запуска и случайного удаления копий.

Пока эти условия не согласованы и не проверены, автоматический триггер не добавлять. Не считать наличие ручной копии полноценной автоматической стратегией.

## 6. Критерии закрытия SAFE-01 / FC-11 / FC-12

- **SAFE-01:** исходная таблица не изменялась; резервная копия создана и проверена; права доступа сохранены.
- **FC-11:** согласованы расписание/retention и независимое хранение; автоматическое резервирование реализовано и проверено либо явно принято решение оставить ручной процесс с документированным расписанием и ответственным.
- **FC-12:** выполнено восстановление в отдельную тестовую таблицу; проверены листы, строки, заголовки, аутентификация, связи и API; исходная таблица не затронута.

До выполнения критериев прогресс чек-листа не увеличивать.
