# Резервное копирование и восстановление — безопасный runbook

20 ноября 2026 года ручная процедура прошла пробу на двух закрытых копиях TEST. Результаты и ограничения приведены в разделе 7. Расписание автоматических копий пока не задано.

## 1. Границы и запреты

- Все пробные действия выполнять только на отдельной тестовой Google-таблице и тестовом Apps Script.
- Не восстанавливать данные поверх исходной таблицы. Восстановление выполняется в новую отдельную копию.
- Не открывать доступ к резервной таблице по ссылке и не добавлять лишних редакторов.
- Не помещать в Git, этот документ, логи или обычные текстовые архивы значения паролей, password hashes, session tokens, Telegram-токены, webhook secrets или другие секреты.
- Не запускать тест восстановления на рабочей таблице. Не менять Production deployment, основной Apps Script или действующий Telegram webhook.
- До первого теста сверить ID исходной и целевой таблицы визуально в адресной строке. Если есть сомнение — остановиться.

## 2. Что входит в состояние приложения

### 2.1. Данные Google Sheets

Текущая схема из `TABLES` в `google-apps-script/Code.gs`:

- `profiles`
- `families`
- `family_members`
- `categories`
- `accounts`
- `transactions`
- `recurring_payments`
- `budgets`
- `goals`
- `goal_contributions`
- `planned_purchases`
- `monthly_plans`
- `notifications`
- `telegram_links`
- `telegram_link_codes`

Дополнительно существует скрытый лист `_auth` с email, солью и хешем пароля. Его нужно сохранить для восстановления входа, но он содержит чувствительные данные и должен оставаться закрытым. Не раскрывать лист и не копировать его содержимое в отдельные файлы.

Копия Google Sheets должна содержать все перечисленные листы и `_auth`, включая заголовки, строки, скрытое состояние и форматирование. CSV из отчётов не является полной копией.

### 2.2. Исходный код и конфигурация

Хранятся отдельно от таблицы:
- исходники Apps Script и `appsscript.json` в Git, ветка `ispravleniya`;
- настройки Apps Script deployment (URL, версия, execute-as, access);
- OAuth scopes и выданные разрешения;
- настройки Preview/Production Vercel;
- настройки Telegram webhook и токен бота.

Копия Spreadsheet сама по себе не доказывает, что связанный Apps Script, его свойства и deployment восстановлены. После создания копии необходимо открыть Extensions → Apps Script и отдельно проверить, какой проект связан с копией. Не предполагать, что копирование таблицы корректно скопировало/перенастроило скрипт.

### 2.3. Script Properties

По текущему `Code.gs` обнаружены следующие ключи и пространства имён:

| Ключ / шаблон | Назначение | Как обращаться при восстановлении |
|---|---|---|
| `TELEGRAM_BACKEND_SECRET` | Секрет внутренней проверки Telegram webhook | Повторно задать безопасным способом в свойствах тестового Apps Script; не записывать значение в Git |
| `SIGNUP_DISABLED` | Флаг закрытой регистрации | Проверить вручную; при необходимости задать `1`, иначе удалить |
| `DEBUG_INFO` | Включает имя таблицы в GET-ответе | Должен быть удалён/выключен на публичном deployment |
| `session:*` | Временные сессии пользователей | Не переносить; после восстановления пользователи входят заново |
| `loginfail:*` | Временные счётчики неудачных входов | Не переносить |
| `table_revision:v2:*` | Маркеры ревизий для клиентского кэша | Не переносить; после восстановления кэш должен считаться новым |
| `telegram:update:*` | Кэш обработанных Telegram updates | Не переносить |
| `telegram:last_prune` | Время последней очистки update-кэша | Не переносить |

Это инвентаризация по текущему исходному коду, а не снимок реальных свойств live-проекта. Перед восстановлением проверить фактический список ключей в соответствующем Apps Script проекте, не раскрывая значения.

Токен Telegram Bot API обычно задаётся отдельно в среде Vercel/в настройках webhook-интеграции; его наличие и точное место хранения проверять по конфигурации окружения, не печатая значение.

## 3. Ручное создание резервной копии (тестовая среда)

1. Открыть именно тестовую Google-таблицу. Сверить её название и URL/ID с тестовой конфигурацией.
2. Убедиться, что таблица приватная и доступна только необходимым аккаунтам.
3. Выбрать **Файл → Создать копию**.
4. Назвать копию с датой и временем, например `TEST-budget-backup-YYYY-MM-DD-HHmm`. Сохранить её в закрытой папке Google Drive.
5. В Apps Script, связанном с исходной тестовой таблицей, запустить `auditBackupStructure()` и сохранить только структурный отчёт.
6. Запустить ту же функцию из Apps Script, связанного именно с копией. Если копия не получила отдельный bound project, создать временный проект, связать его с копией и загрузить проверенный `Code.gs` из ветки `ispravleniya`. Не запускать скрипт исходной таблицы, предполагая, что он проверит копию: функция использует активную таблицу своего bound project.
7. В обоих отчётах должны совпасть наличие листов, заголовки и количества строк; `_auth` должен быть скрыт, timezone — `Europe/Moscow`, `allChecksPassed` — `true`. Функция не проверяет права доступа и не сравнивает содержимое строк — это отдельные ручные проверки.
8. Убедиться, что копия не получила более широкие права доступа, чем исходная таблица.
9. Зафиксировать имя файла, дату/время, владельца и факт проверок в закрытом операционном журнале. Не записывать в Git ID таблицы, если репозиторий публичный, и не записывать данные строк.

Если какой-либо лист отсутствует, заголовки отличаются или права доступа расширились — считать копию непроверенной и не использовать её для восстановления.

## 4. Пробное восстановление (только в новую тестовую копию)

1. Выбрать проверенную резервную копию тестовой таблицы.
2. Через **Файл → Создать копию** создать ещё одну новую таблицу для восстановления. Не использовать исходную таблицу и не перезаписывать резервную копию.
3. Проверить все листы и заголовки по разделу 2.1, включая скрытый `_auth`. Проверить количества строк без публикации значений.
4. Открыть Apps Script из новой таблицы. Проверить привязку проекта; если проект отсутствует или связан с другой таблицей, создать/подключить отдельный тестовый проект и загрузить проверенные исходники из ветки `ispravleniya`. Не подключать этот проект к основной таблице.
5. Запустить `auditBackupStructure()` из проекта, связанного с новой таблицей. Продолжать только если `allChecksPassed=true`; сравнить числа строк с отчётом проверенной резервной копии.
6. Проверить manifest: `Europe/Moscow`, V8. Отдельно проверить фактические project timezone и spreadsheet timezone. Manifest в Git не подтверждает фактические настройки проекта.
7. Настроить только необходимые тестовые Script Properties. Секрет `TELEGRAM_BACKEND_SECRET` должен быть отдельным тестовым значением; не использовать production secret. Удалить/не создавать `DEBUG_INFO`. Проверить желаемое состояние `SIGNUP_DISABLED`.
8. Не переносить transient keys `session:*`, `loginfail:*`, `table_revision:v2:*`, `telegram:update:*`, `telegram:last_prune`. Считать, что пользователям потребуется повторный вход, а кэш будет построен заново.
9. Создать отдельное тестовое web-app deployment. Не менять существующий Production deployment и не менять рабочий Telegram webhook. Если требуется проверить Telegram, использовать отдельный тестовый бот и отдельный тестовый webhook.
10. Проверить API health/version без включения `DEBUG_INFO`. Проверить вход тестового пользователя, чтение нескольких тестовых записей и сохранность связей между семьёй, участниками, счетами, категориями и операциями.
11. На тестовых данных выполнить одну безопасную запись, затем повторно прочитать её. Проверить, что суммы остаются целыми копейками, даты корректны, а второй тестовый участник видит ожидаемые семейные данные.
12. Зафиксировать результат и удалить тестовые данные/окружение только после сохранения доказательств теста и отдельного решения. Не удалять исходную таблицу или резервную копию.

Успех копирования файла не равен успешному восстановлению. FC-12 можно закрывать только после прохождения всего теста на отдельной копии.

## 5. Что не автоматизировать до отдельного решения

Автоматический backup через `DriveApp` потребует:
- выбранной закрытой папки Google Drive и проверки владельца/прав;
- согласованного расписания и срока хранения (retention);
- проверки квот Google Apps Script/Drive и обработки ошибок;
- явного OAuth scope и повторной авторизации тестового проекта;
- проверки, что копии создаются в ожидаемом месте и остаются приватными;
- мониторинга успешности и оповещения о пропущенном backup;
- защиты от параллельного запуска и случайного удаления копий.

Пока эти условия не согласованы и не проверены, автоматический триггер не добавлять. Не считать наличие ручной копии полноценной автоматической стратегией.

### Предлагаемая схема для TEST

Для согласования с владельцем предлагается одна копия в неделю и четыре недельных снимка. Периодичность, срок и место независимого хранения остаются открытыми решениями владельца. Сейчас действует ручной процесс.

1. Исполнитель работает только с заранее выбранной исходной TEST-таблицей и закрытой папкой. Перед копированием он сверяет идентификаторы, владельца и список получателей доступа. При общем доступе или изменении владельца запуск останавливается.
2. Под одной блокировкой исполнитель ищет запись за текущую неделю по московскому времени. При повторном запуске он продолжает проверку уже созданной копии. Если её нет, создаёт новую копию. Журнал связывает неделю с идентификатором файла и состоянием проверки.
3. Копия считается принятой после сверки прав, обязательных листов, заголовков, часового пояса, скрытого служебного листа и числа строк с отчётом источника. Если во время копирования менялась исходная таблица, снимок отмечается как требующий повторной проверки. В операционном журнале остаются время, статус и имя файла.
4. При ошибке предыдущий принятый снимок сохраняется. Исполнитель записывает причину без данных строк. Для пропущенного срока или неудачной проверки требуется согласованный с владельцем способ оповещения. Повторный запуск продолжает работу с той же недельной записью.
5. Периодически владелец выбирает принятый снимок и проверяет восстановление в новый файл по разделу 4. Удаление старых снимков, подключение независимого хранилища и запуск по расписанию требуют отдельного согласования. Резервная и восстановленная копии этой пробы хранятся в одном закрытом Drive владельца.

## 6. Критерии закрытия SAFE-01 / FC-11 / FC-12

- **SAFE-01:** исходная таблица не изменялась; резервная копия создана и проверена; права доступа сохранены.
- **FC-11:** согласованы расписание/retention и независимое хранение; автоматическое резервирование реализовано и проверено либо явно принято решение оставить ручной процесс с документированным расписанием и ответственным.
- **FC-12:** выполнено восстановление в отдельную тестовую таблицу; проверены листы, строки, заголовки, аутентификация, связи и API; исходная таблица не затронута.

До выполнения критериев прогресс чек-листа не увеличивать.


## 7. Проба на отдельной TEST-копии 20 ноября 2026 года

- Владелец исходного файла, закрытой папки, резервной и восстановленной таблиц совпал. У каждого объекта одна запись доступа с ролью владельца. Имена файлов и время создания хранятся отдельно в операционном журнале.
- При копировании проекты унаследовали явные OAuth-права на все таблицы и внешние запросы. На двух привязанных проектах область доступа ограничена `https://www.googleapis.com/auth/spreadsheets.currentonly`. В обзоре каждого проекта Google показал одну область. Владелец подтвердил именно этот доступ. Для запуска структурного аудита и штатного обработчика Family Cash его оказалось достаточно. Диагностики, которым требуется внешний HTTP-запрос, в этих копиях не запускались.
- Проверенная версия `Code.gs` — v11 из 25d49fb1. В обеих копиях проект использует V8 и московский часовой пояс. Отчёты `auditBackupStructure()`, полученные в собственных привязанных проектах копий до пробной записи, полностью совпали с сохранённым отчётом источника. Проверены 16 обязательных листов, их заголовки, скрытое состояние служебного листа и количество заполненных строк по каждому листу.
- Для профилей, семей, членства, категорий, счетов и операций отдельно сверены заполненные на момент снимка строки по полям идентификаторов и связей, а для операций также даты и целые суммы в копейках. Пустые в снимке ссылки на счета проверены отдельно от заполненных. Сохранённые значения совпали между источником (строки снимка), резервной и восстановленной таблицами. Проверка обнаружила исходную семью, чей создатель отсутствует среди профилей. У неё 87 категорий, 0 участников и 0 операций. Расхождение присутствовало уже в источнике. Ремонт исторических данных требует отдельного решения владельца.
- Закрытый пробный адрес `/dev` восстановленного проекта вернул `status=ok` и версию API 11 без имени таблицы. Внутри восстановленного проекта через штатный `doPost` два новых синтетических пользователя зарегистрировались, вышли, повторно вошли, создали семью и присоединились к ней. Второй участник прочитал созданный первым тестовый счёт. Пробная расходная запись сохранила дату, целое число копеек, ссылки на семью, счёт и категорию и разных автора и ответственного. Оба участника прочитали одну и ту же запись. Оба сеанса завершены. Пробная запись осталась только в восстановленной копии. Временная функция удалена из черновика, сохранённый `Code.gs` перечитан и полностью совпал с v11.
- Для этого прогона HTTP-проверка `/dev` охватывала GET. Вызовы `doPost` выполнялись в привязанном проекте с входным событием Apps Script. Пароль пользователя, существовавшего до снимка, в проверке не использовался. Строки служебного листа с учётными данными не экспортировались.

- После согласия владельца в восстановленном проекте опубликована отдельная версия развертывания 1 от 20.11.2026 23:33 МСК. В управлении развертываниями подтверждены тот же постоянный адрес и доступ «Только у меня». По постоянному `/exec` в сеансе владельца получены `status=ok`, `version=11` и только поля status, message, version. На настольном компьютере из меню «Файл» восстановленной таблицы открыта панель «История версий» и видна текущая версия. По шести критериям FC-12 проверка восстановления TEST пройдена. Ограничения проверки входа и HTTP POST приведены выше.
