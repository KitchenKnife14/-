# Family Cash — матрица регрессионных тестов

> Версия: 1.0  
> Дата: 2026-11-10  
> Ветка: `ispravleniya`  
> Назначение: превратить статические находки аудита в воспроизводимые проверки до исправления кода.  
> Статус: матрица подготовлена; новые тесты ещё не добавлены и не запускались.

## 1. Правила выполнения

1. Локальные тесты запускаются только на изолированном VM-harness и синтетических данных.
2. Apps Script runtime-тесты запускаются только на отдельном тестовом Apps Script Web App и отдельной тестовой Google Sheet.
3. Запрещено направлять harness, скрипты, ручные запросы или fault-injection на Production URL и таблицу «Семейный бюджет».
4. Не использовать реальные финансовые записи в фикстурах. Сценарии строятся на синтетических семьях, пользователях, счетах, категориях и операциях.
5. Дефектные сценарии сначала фиксируются как ожидаемо падающие regression tests на тестовой копии кода. После исправления они должны стать зелёными.
6. Не объединять независимые дефекты в один тест: один тест должен иметь одну основную причину отказа.
7. Тесты не должны использовать эвристическую дедупликацию по сумме/описанию/дате. Два одинаковых расхода с разными ID — две законные операции.
8. До любых изменений в тестах/коде зафиксировать HEAD и список файлов; изменения объединять в логические коммиты.

## 2. Уровни тестирования

| Уровень | Что проверяется | Среда |
|---|---|---|
| L0 — статический контракт | типы входов, поля, ветвления, allowlist, отсутствие опасных вызовов | review/grep |
| L1 — unit | валидаторы, money helpers, parser, account balance calculations | Node.js |
| L2 — backend VM | doPost/query/RPC, права, таблицы, частичные ошибки, идемпотентность | существующий VM-harness, синтетические Sheets |
| L3 — Apps Script integration | реальные ограничения LockService, PropertiesService, Sheets, execution/runtime | только отдельный тестовый Apps Script + Sheet |
| L4 — frontend | формы, фильтры, отображение, адаптивность, клавиатура | компонентные/browser tests и реальные viewport |
| L5 — E2E | UI → Vercel webhook → тестовый Apps Script → тестовая Sheet; повторы и итоговые данные | только изолированная тестовая цепочка |

## 3. Существующее покрытие — подтверждённый baseline

В `tests/apps-script.test.cjs` обнаружено 65 объявлений `test()`; это статический подсчёт, не результат запуска. Существующие проверки уже затрагивают:

- signup/signin, rate limit, rollback signup;
- семейную изоляцию, запрет чужих ссылок и изменение автора;
- защиту личных уведомлений;
- повторные подтверждения recurring payment / planned purchase после частичной записи;
- goal contributions и пересчёт saved total;
- защиту удаления используемого счёта и валидацию transfer-счетов;
- бюджеты, monthly plans, миграции схемы;
- PBKDF2 и legacy hash migration;
- Telegram linking, секрет, одноразовый код, несколько чисел и атрибуцию;
- классификатор ScriptLock и baseline, что read-only query пока получает глобальную блокировку.

В `tests/account-balances.test.cjs` находятся отдельные тесты расчёта остатков. Текущее наличие этих файлов не подтверждает, что они запускались в этой рабочей сессии.

## 5. Проверка качества самого test harness

Перед доверием к L2/L3 необходимо усилить/проверить harness:

- [ ] `LockService.waitLock()` сейчас только увеличивает счётчик; это не моделирует contention, timeout, ownership или конкуренцию.
- [ ] `SpreadsheetApp` mock возвращает одну и ту же таблицу для `getActiveSpreadsheet()` и `openById()`; тесты не доказывают корректность выбора изолированной таблицы.
- [ ] Нет полноценного моделирования сетевого timeout и прерывания выполнения Apps Script между двумя side effects.
- [ ] Нет достоверной параллельной модели для двух одновременных doPost.
- [ ] Mock Range/Sheet реализует только используемую часть API; отсутствие ошибок в VM не доказывает совместимость с реальным Apps Script runtime.
- [ ] VM сейчас загружает только `google-apps-script/Code.gs` из ветки. Пользовательский загруженный Code.gs — отдельный кандидат для тестирования; его более новый Telegram parser нельзя считать покрытым этим harness, пока файл не включён в отдельный fixture/test target.
- [ ] Fault injection должен быть адресным: ошибка после transaction insert, до update_id cache write; ошибка после первой записи compound RPC; повторная доставка после каждого частичного состояния.
- [ ] Любой тест, который использует `setupSheets()` или `selfTest()`, должен работать только на синтетической таблице. В пользовательском Code.gs selfTest создаёт и удаляет временный лист.

## 6. Порядок реализации тестов

**Пакет T1 — P1 деньги и ссылки:** MONEY-01..09, CAT-01..09.  
**Пакет T2 — дубли и Telegram:** IDEM-01..08, TG-01..15, WEB-07.  
**Пакет T3 — безопасность и concurrency:** SEC-01..08, LOCK-01..04.  
**Пакет T4 — UI и E2E:** UI-01..09, WEB-01..08.

Порядок для каждого пакета:
1. Добавить независимые regression tests к изолированному harness.
2. Зафиксировать ожидаемый текущий отказ (red) и убедиться, что тест действительно ловит дефект.
3. Исправить реализацию минимальным логическим изменением.
4. Запустить целевой пакет и весь `npm test`.
5. Запустить `npm run typecheck` и `npm run build`, если менялись frontend/общие типы.
6. Только после локальной проверки переносить серверный сценарий в отдельный тестовый Apps Script.
7. Записать фактический результат, команду, SHA и ограничения.

## 7. Критерии завершения этапа 4

- Известные ограничения VM-harness документированы.
- Существующее покрытие отделено от отсутствующего.
- Новые regression tests воспроизводят дефекты на изолированной копии; они не запускаются против Production.
- Команды запуска и результаты сохранены в журнале.
