## 0. Главные правила безопасности и управления изменениями

1. **Не терять существующие операции.** Google Sheets «Семейный бюджет» — основная база. Никакие исправления не должны очищать, пересоздавать, переименовывать, сортировать с потерей строк или мигрировать существующие данные без отдельного плана, резервной копии и явного согласования.
2. **Сначала тестовая среда.** Все серверные изменения сначала проверяются в тестовом Google Apps Script и отдельной тестовой таблице. Не использовать рабочую таблицу как тестовую.
3. **Production не трогать до завершения и согласования.** Не менять Production Apps Script, Vercel, webhook, Production env vars, основную таблицу и ветку `main` в ходе подготовительных этапов.
4. **Не публиковать автоматически.** Любое развёртывание, смена URL, секрета, webhook или версии Apps Script требует отдельного согласования и пошагового плана отката.
5. **Не удалять историю.** Не удалять ветки, коммиты, файлы с исходной реализацией, данные, листы или записи. Не делать force-push, reset или destructive migration.
6. **Каждый этап фиксировать.** До работы — цель и перечень файлов; после — изменения, коммиты, тесты, результат, известные ограничения и следующий шаг.
7. **Не повторять выполненное.** Перед каждым этапом сверять этот журнал, текущую ветку, HEAD и существующие тесты.
8. **Одна логическая группа изменений за этап.** Не смешивать финансовую логику, Telegram, UI и крупные обновления зависимостей в одном неразборчивом коммите.
9. **Не считать тесты доказательством отсутствия всех дефектов.** Различать статический анализ, unit-тесты, интеграционные тесты, реальные проверки и непроверенные предположения.
10. **Не раскрывать секреты.** Токены, пароли, значения env vars и секреты Apps Script не помещать в репозиторий, журнал, скриншоты или сообщения.

## FC-18 — React Router security advisory (обязательный отдельный пункт)

### Что подтверждено по коду
- В `package.json` задано `react-router-dom: ^6.26.2`.
- В `package-lock.json` зафиксировано `react-router-dom 6.30.6`; транзитивный `react-router` также разрешается из версии 6.30.6.
- Приложение использует Declarative Mode: `BrowserRouter`, `Routes`, `Route`, `Navigate`.
- В проверенном `App.tsx` переход `Navigate` ведёт на фиксированный внутренний путь `/`.
- В `Layout.tsx` используются статические внутренние маршруты через `NavLink`.
- SSR/Data Router loaders/actions в проверенных точках не обнаружены. Это снижает применимость advisory, связанной именно с SSR hydration, но не отменяет advisory для самого установленного пакета.

### GHSA-wrjc-x8rr-h8h6 / CVE-2026-53669
- Официальная карточка: https://github.com/advisories/GHSA-wrjc-x8rr-h8h6
- Затронутые версии: `react-router >=6.0.0 <7.18.0`.
- Исправленная версия: `7.18.0`.
- Суть: обход предыдущего исправления, при котором недоверенные пути с обратными слешами в навигационных механизмах `<Link>` и `useNavigate` могут привести к неожиданной внешней навигации.
- Версия 6.30.6 попадает в объявленный диапазон уязвимых версий.
- Наличие уязвимой версии в lockfile подтверждено. Факт успешной эксплуатации именно в Family Cash не установлен.

## 4. Протокол проверки каждого этапа

Для каждого этапа обязательно фиксировать:

1. **Перед началом:** дата, ветка, HEAD, базовый SHA, проблема, цель.
2. **Изучение:** точные файлы, функции, строки, связанные тесты, внешние advisories.
3. **План правки:** что будет изменено и что намеренно не меняется.
4. **Изменения:** список файлов и commit SHA.
5. **Тесты:** точные команды, количество тестов, pass/fail, build/typecheck.
6. **Проверка данных:** тестовая таблица/фикстуры, количество записей до/после, отсутствие удаления и дублирования.
7. **Итог:** исправлено / частично / не воспроизведено / заблокировано.
8. **Откат:** commit или точный способ вернуть изменения без потери последующих коммитов.
9. **Следующий шаг:** только один следующий логический этап.

## LOCK-01 — глобальная блокировка Apps Script

**Критический приоритет P1.**

### Подтверждено в исходнике ветки ispravleniya

Файл: google-apps-script/Code.gs, функция doPost(e).

- В начале обработки создаётся LockService.getScriptLock().
- Для telegramWebhook вызывается waitLock(20000), после чего блокировка удерживается на протяжении всей функции telegramWebhook_(req).
- Для всех остальных POST-действий также вызывается waitLock(20000).
- Внутри общей блокировки выполняются signup, signin, signout, batch и все остальные маршруты через requireUser_() и route_().
- Следовательно, под блокировкой находятся и обычные запросы чтения: query с режимом select, getSession, getUser, get_table_revision, а также записи и составные RPC.
- Блокировка освобождается в finally; при ошибке до получения блокировки выполняется дополнительная проверка hasLock().
- В лог выполнения уже выводятся lockMs, workMs, totalMs, число чтений/записей и время чтения/записи. Это полезная основа для измерения, но текущий тестовый harness реальные конкурентные ожидания блокировки не моделирует.
- В batch пакет из нескольких операций исполняется последовательно, пока внешний doPost держит ту же блокировку.
- В telegramWebhook_ блокировка защищает проверку/запись Telegram update id от гонки повторной доставки. Удалять эту защиту без замены нельзя.
- Signup сериализуется для защиты от одинаковых email; join/create family и некоторые составные изменения также полагаются на текущую сериализацию запросов.

### Важное уточнение о масштабе проблемы

Фраза «каждый POST блокируется» подтверждается для обычного пути и Telegram webhook, но doGet() не использует эту блокировку. Блокировка берётся после разбора JSON и проверки action. Все POST-операции при этом конкурируют за один ScriptLock.

### Почему нельзя просто убрать waitLock

Простое удаление блокировки может создать гонки:
- два signup одного email одновременно;
- два join/create family одновременно;
- повторная доставка одного Telegram update;
- одновременное обновление/удаление одних строк;
- конфликты между составными операциями, меняющими несколько листов;
- race conditions при использовании ScriptProperties и ревизий таблиц.

### Критерий завершения LOCK-01

Не просто «waitLock удалён», а:
1. read-only запросы не блокируются длительными независимыми операциями записи там, где это безопасно;
2. конфликтующие изменения данных остаются защищены;
3. Telegram update idempotency не регрессирует;
4. signup/join/create family остаются безопасными при конкуренции;
5. тесты конкуренции и регрессии проходят;
6. измерения показывают снижение ожидания чтения;
7. все изменения находятся в ветке ispravleniya, Production и основная таблица не затронуты.

### SEC-03 — проектирование семейных ревизий и polling (работа № 29)

- Проверен полный путь ревизий: `appendRows_`, `updateRows_`, `deleteRows_` и `writeRows_` вызывают `touchTableRevision_(name)`; helper записывает один глобальный ScriptProperties ключ `table_revision:<table>`. RPC `get_table_revision` проверяет только наличие хотя бы одного семейного членства, после чего читает этот глобальный ключ.
- Проверен frontend `src/lib/googleSheets.ts`: подписка раз в 15 секунд вызывает RPC `get_table_revision` только с `p_table`; идентификатор семьи клиент не передаёт. Фильтр подписки хранится в callback-подписке, но не участвует в формировании серверной ревизии. При смене ревизии вызывается callback, который затем перечитывает данные через обычные query.
- Установлено важное ограничение текущей модели: `joinFamily` отклоняет присоединение пользователя, который уже состоит в другой семье; `get_my_context` также выбирает одну первую membership как текущую семью. Поэтому сейчас у пользователя не должно быть нескольких семейных пространств. Это позволяет сохранить frontend RPC-контракт без передачи family_id: сервер может сам получить единственную разрешённую семью из `allowedFamilyIds_(user)`.
- Безопасный целевой контракт: ключ ревизии должен включать family_id и таблицу (например, `table_revision:<familyId>:<table>`). Чтение RPC должно вычислять family_id только на сервере из членства текущего пользователя и никогда не принимать произвольный family_id от клиента. Для отсутствия членства — отказ; для таблиц без семейного контекста — отдельное явно определённое поведение, а не fallback на глобальную ревизию.
- Перед реализацией требуется закрыть матрицу записи: обычные append/update/delete/write должны обновлять ревизии всех семей, чьи строки реально затронуты; `goal_contributions` не содержит собственного `family_id`, поэтому семейный идентификатор нужно получать через родительскую goal; для специальных RPC и каскадных операций надо проверить, что каждый изменяемый лист проходит через общий helper и что ревизия не пропускается при нескольких последовательных записях.
- Миграция должна быть совместима с текущими клиентами: имя RPC, аргументы `p_table` и тип возвращаемой строки остаются прежними. На первом чтении нового ключа допустимо вернуть стабильное начальное значение, но нельзя временно отдавать старую глобальную ревизию — это снова раскроет межсемейную активность. Старый глобальный ключ можно оставить неиспользуемым до отдельной безопасной очистки; очистка не нужна для исправления утечки.
- Текущий helper подавляет исключения при записи ревизии (`try/catch` без логирования). Это отдельный reliability-риск: после успешной записи данных ошибка ScriptProperties может оставить polling без сигнала. При реализации надо решить, должна ли ошибка ревизии приводить к ошибке запроса или фиксироваться как диагностируемый degraded state; нельзя допускать ложного сообщения об успешной записи при потере данных, но и нельзя провоцировать небезопасный повтор финансовой операции после уже выполненной записи.

Зафиксирован проект миграции; следующий шаг — инвентаризация всех write sites и параметризованные тесты семейных ревизий, затем отдельная реализация с обратной совместимостью. ### CONC-01 — аудит ScriptLock, batch и частичных записей (работа № 31)

- `doPost` получает один глобальный `LockService.getScriptLock()` и вызывает `waitLock(20000)` для всех обычных действий, включая чтение, авторизацию и batch; отдельный webhook также сериализуется тем же глобальным lock. Это исключает параллельное выполнение обработчиков в рамках одного Apps Script проекта, но создаёт общую очередь и риск таймаута ожидания 20 секунд при нагрузке. `requestLockMode_()` пока только классификатор для тестов и никак не меняет `doPost`.
- Тесты подтверждают только baseline: read-only query вызывает acquire/release ScriptLock; сами тесты используют синхронную заглушку LockService. Реальные конкурирующие исполнения GAS, lock timeout, lock ownership и starvation не моделируются. Поэтому нельзя считать race conditions проверенными.
- `batch_()` обрабатывает элементы последовательно через `list.map`, каждый элемент имеет собственный `try/catch`; пакет не является транзакцией. Если ранние операции записи прошли, а последующая вернула ошибку, предыдущие изменения остаются. Frontend adapter при частном ответе распределяет success/error по элементам; при неоднозначном сетевом timeout весь batch может быть отклонён клиентом, даже если часть/все операции уже обработаны сервером. Для финансовых insert это требует устойчивого request ID.
- Частичные write paths: `appendRows_` выполняет один `setValues` и затем обновляет ревизию; `updateRows_` может выполнять несколько раздельных `setValues` групп и вызывает `touchTableRevision_` только после завершения всех групп; `deleteRows_` может выполнять несколько раздельных `deleteRows` и обновляет ревизию только после всех групп. Если промежуточная группа упадёт, предыдущие изменения уже могли сохраниться, а revision не будет обновлена. Это конкретный риск stale UI и повторного действия после частичного commit.
- `touchTableRevision_` подавляет все ошибки ScriptProperties без логирования. Даже после полного успешного изменения листа polling-сигнал может быть потерян. В связке с частичным update/delete это делает ревизию ненадёжным commit marker; она должна считаться только сигналом обновления, но не источником истины о транзакционном результате.
- `writeRows_` реализует полную перезапись данных и очистку хвоста, но в текущем Code.gs по поиску вызовов найдено только определение функции, без call sites. Прямые записи `setValues` вне общих helpers относятся к заголовкам листов, auth sheet и self-test; рабочие CRUD-пути используют общие helpers.
- Уже существуют узкие recovery tests для `confirm_recurring_payment` и `confirm_planned_purchase`: моделируется ошибка при обновлении родительской записи после вставки транзакции, затем повтор RPC; deterministic transaction ID предотвращает дубликат. Это полезное покрытие двух специальных RPC, но не доказывает общую атомарность Google Sheets и не моделирует отказ реального Spreadsheet service между несколькими группами записи.
- Рекомендация: не заменять ScriptLock на read/write lock сейчас. Сначала отдельно решить семантику частичного commit и ревизий, добавить fault-injection tests для отказа после первой успешной группы update/delete и для отказа ScriptProperties; затем измерить lock wait на тестовом GAS. Не заявлять атомарность операций Google Sheets там, где её не гарантирует текущая последовательность вызовов.
- Код не изменялся. Проверка основана на исходниках и Node VM harness; реальные GAS concurrency и fault injection остаются незавершёнными. Production, основная таблица, опубликованный Apps Script, Vercel и Telegram webhook не менялись.

### TG-04 — аудит webhook timeout и повторной отправки ответов (работа № 32)

- Проверен `telegram-webhook/handler.ts`: обе внешние операции (`fetch` к Apps Script и `fetch` к Telegram `sendMessage`) выполняются без собственного `AbortSignal`/таймаута. Поэтому время их завершения ограничено только средой выполнения/платформой, а не явным бюджетом времени обработчика. Автоматически добавлять Abort timeout нельзя: timeout не доказывает, что удалённая сторона не выполнила действие.
- Backend `telegramWebhook_` сначала обрабатывает update, записывает операцию с детерминированным ID `telegram_<update_id>` и сохраняет ответ в ScriptProperties на 24 часа; при повторном update возвращает закэшированный reply. Это предотвращает повторную финансовую запись при retry, если первый запрос дошёл до backend и запись/кэш были сохранены.
- Найдено окно неоднозначности на отправке ответа: Vercel handler вызывает Telegram `sendMessage` после того, как backend уже сохранил reply. Если Telegram принял сообщение, но ответ `sendMessage` потерялся/таймаутнул, handler вернёт 502; Telegram может повторить webhook, backend вернёт cached reply, и handler отправит его ещё раз. В результате финансовая операция остаётся одна, но пользователь может получить дублированное текстовое подтверждение.
- Обратный сценарий тоже возможен: если ответ backend был потерян до того, как Vercel получил его, повтор webhook получает сохранённый reply и пытается отправить его; это корректно для доставки ответа, пока Telegram ещё не получил первое сообщение. Следовательно, нельзя просто пропускать отправку при повторном update: это устранит дубли, но создаст риск потерянного ответа.
- Telegram Bot API `sendMessage` в текущем запросе не получает request id/idempotency key; код не ведёт отдельное состояние отправки в outbox. Но даже добавление локального флага `sent=true` до вызова Telegram не обеспечивает exactly-once: падение между флагом и отправкой потеряет ответ, а флаг после отправки оставляет исходное окно ambiguous result. Для надёжного решения нужен осознанный at-least-once / best-effort контракт или отдельная reconciliation-стратегия; гарантировать exactly-once доставку по текущему API пути нельзя.
- Тесты `tests/telegram-webhook.test.cjs` проверяют 11 сценариев, включая backend non-2xx/non-JSON, обычную успешную отправку и отказ Telegram, но не моделируют зависший fetch, AbortSignal, ответ Telegram `ok:true` с последующей потерей соединения или повтор того же update после неоднозначной отправки.
- Не менял handler и не добавлял timeout: сначала требуется выбрать продуктовую семантику ответа при неизвестном результате `sendMessage`, а затем покрыть retry/failure tests. Логи не раскрывают токены, текст сообщений или финансовые данные; catch возвращает общий 502.
