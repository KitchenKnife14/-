# Аудит доступа к семейным финансам — 2026-11-17

> Область: исходный код ветки `ispravleniya`; не является подтверждением состояния Production Script Properties или опубликованных deployments.

## 1. Проверенные механизмы

### Вход на сайт и серверная авторизация

- Все пользовательские действия, кроме явных публичных действий `signup`, `signin` и `telegramWebhook`, проходят через `requireUser_(req.token)` в Apps Script.
- Сессия проверяется на сервере по Script Properties: токен должен существовать, JSON должен иметь корректный `userId` и неистёкший срок действия. Срок — 14 дней; `signout` удаляет серверную сессию.
- Токен фронтенда хранится в `localStorage`. Это означает, что успешная XSS-атака на сайт могла бы прочитать токен. В просмотренных файлах конкретный XSS-вектор не подтверждён; это остаётся защитным ограничением, а не доказанным эксплойтом.
- `AuthPage` показывает регистрацию. Backend умеет запрещать её через Script Property `SIGNUP_DISABLED=1`, но фактическое значение этого свойства в Production недоступно для проверки из GitHub.

### Разделение семейных данных

- Сервер строит список доступных family ID из `family_members`.
- Чтение, обновление и удаление строк ограничиваются проверкой принадлежности текущему пользователю; уведомления дополнительно ограничиваются собственным user ID.
- Insert/upsert и семейные RPC проверяют family membership и связанные сущности.
- В тестах есть отдельные проверки прямого API, batch, cross-family isolation для family-scoped tables, RPC с чужим family ID, чужих профилей и персональных уведомлений.

### Telegram

- Vercel endpoint принимает только POST, проверяет Telegram secret header, проверяет конфигурацию секретов и разрешает только ожидаемый HTTPS Apps Script Web App URL.
- Apps Script дополнительно проверяет отдельный `TELEGRAM_BACKEND_SECRET`.
- Обрабатываются только личные чаты; привязка использует Telegram user ID, одноразовый код и проверку актуального членства в семье.
- `/balance` и создание операции повторно проверяют, что Telegram user ID связан с пользователем, который всё ещё состоит в указанной семье.
- Служебные таблицы `telegram_links` и `telegram_link_codes` запрещены в обычном публичном CRUD API.
- В тестах есть проверки неверных секретов, одноразовой привязки, запрета подделки Telegram link rows через общий API, повторной доставки, коллизии update_id и изоляции баланса.

## 3. Открытые вопросы и ограничения

1. **Production registration flag:** из кода известно, что `SIGNUP_DISABLED=1` блокирует регистрацию. Я не могу подтвердить, что это свойство действительно установлено в Production. Публичная форма регистрации при этом остаётся видимой; окончательное решение принимает backend.
2. **localStorage session:** токен доступен JavaScript текущего origin. Без подтверждённого XSS это не доказывает уязвимость, но снижает защиту от последствий XSS.
3. **HTTP security headers:** текущий `vercel.json` содержит build, output и SPA rewrite, но не задаёт CSP, HSTS, frame restrictions или другие security headers. Их добавление требует аккуратной CSP-настройки и browser regression, чтобы не сломать Apps Script fetch и загрузку шрифтов.
4. **Production state:** этот аудит не читает Production Script Properties, реальные таблицы, Vercel Production environment или опубликованный webhook. Поэтому нельзя сертифицировать фактическую конфигурацию Production по одному репозиторию.

## 4. Следующий порядок

1. Добиться выполнения CI для текущего security patch; Vercel checks сейчас показывают `build-rate-limit`, а GitHub Actions run для последнего коммита не обнаружен. Это не является результатом тестирования кода.
2. Перенести актуальный `Code.gs` только в изолированный TEST GAS и повторить regression/runtime acceptance. Не менять Production.
3. После успешной TEST-приёмки проверить значение `SIGNUP_DISABLED=1` в Production Script Properties вручную.
4. Отдельно проверить CSP/security headers и browser поведение; не включать строгую CSP без проверки всех внешних соединений.
