# AGENTS.md — «Бюджет для двоих»

## Проект и обязательная архитектура
- Приватное семейное приложение для двух пользователей.
- Frontend: React 18, TypeScript, Vite, Tailwind CSS, React Router.
- Основное хранилище: Google Sheets. Серверный слой и API: Google Apps Script Web App.
- Frontend размещается на Vercel.
- Язык интерфейса — русский; валюта — RUB/₽; часовой пояс — Europe/Moscow.
- Не заменять Google Sheets / Apps Script другим backend и не вводить второе хранилище без прямого согласования владельца.
- Денежные значения хранить и передавать целыми копейками. Валидировать безопасный целочисленный диапазон.

## Безопасность и финансовая целостность
- Таблица Google Sheets должна оставаться закрытой. Не публиковать её и не выдавать клиенту прямой доступ к редактированию.
- Все права, семейную принадлежность и допустимость изменений проверять на стороне Apps Script. Нельзя доверять family_id/user_id/created_by, пришедшим от клиента.
- Не хранить пароли в открытом виде. Не выводить пароли, токены, секреты или содержимое служебного листа _auth в логи и ответы.
- Не раскрывать имена листов, структуру _auth, внутренние stack traces и чувствительные данные в публичных ответах.
- Защищать все update/delete фильтрами; запретить неограниченные массовые изменения из обычного API.
- Для критичных многошаговых операций использовать LockService, короткую критическую секцию, try/finally и компенсирующий откат там, где Sheets не обеспечивает транзакцию.
- Не объявлять многошаговые изменения Google Sheets ACID-транзакциями.
- Частичный сбой не должен маскироваться под успешную операцию. Учитывать retry/idempotency, чтобы повтор не создавал дубликаты.
- Переводы между счетами должны отражаться с обеих сторон; переводы не являются доходом или расходом семьи.
- Запланированные операции не должны попадать в фактические суммы.
- Снятия с цели допустимы только если сумма движений по цели после операции не отрицательна.
- Не удалять финансовую историю вследствие удаления вспомогательных сущностей без ясной спецификации и подтверждения.

## Google Sheets / Apps Script
- Не переписывать целые листы при изменении одной строки.
- Предпочитать пакетные чтения/записи и затрагивать только изменённые диапазоны.
- Не выполнять повторное открытие одной и той же таблицы и чтение одних листов внутри запроса без причины.
- Учитывать лимиты времени и квоты Apps Script.
- Все заголовки листов и порядок колонок валидировать.
- Добавление колонок и листов должно быть совместимым и документированным.
- Сериализовать конфликтующие записи через LockService.
- Не вводить длительные глобальные блокировки для обычного чтения без необходимости.
- Любое разделение чтения/записи должно сохранять согласованность снимка данных и не показывать промежуточное состояние многошаговой записи.
- Не публиковать Apps Script и не менять Web App deployment без отдельного разрешения владельца.

## Frontend / UX
- Сохранять существующие маршруты и бизнес-функции при редизайне.
- Все пользовательские тексты писать на русском.
- Для загрузки, ошибок и пустых данных предусматривать отдельные состояния.
- Удаления и другие разрушительные действия подтверждать понятным диалогом.
- Не терять введённые данные при сетевых ошибках и обновлениях состояния.
- Mobile-first: проверить ширины 375–390 px, iPhone safe areas, клавиатуру, прокрутку, модальные окна и горизонтальное переполнение.
- Соблюдать prefers-reduced-motion и доступность клавиатурной навигации.
- Не добавлять зависимости без обоснования.

## Скорость
- Измерять фактические задержки и число обращений к Apps Script / Google Sheets до и после оптимизации.
- Сохранять batching, объединение одинаковых запросов и кэширование только при корректной инвалидации.
- Не допускать, чтобы кэш скрывал свежие финансовые операции дольше заявленного интервала обновления.
- Не называть пакетный размер, gzip или локальный бенчмарк реальным временем загрузки сайта.
- Не создавать лишние Vercel deployments: квоты могут быть ограничены.

## Telegram
- Данные Telegram и финансовые сводки получать только через Apps Script после проверки привязанного пользователя и семейных прав.
- Привязка должна быть индивидуальным одноразовым токеном с ограниченным сроком жизни, а не одним общим семейным кодом.
- Дедуплицировать update_id, ограничивать частоту, защищать от повторного выполнения, не журналировать токены.
- Проверять Telegram webhook secret на том слое, где доступен HTTP-заголовок; не предполагать, что Apps Script doPost(e) предоставляет произвольные headers.
- Не отправлять персональные финансы в групповые чаты по умолчанию.
- Начинать с read-only команд и уведомлений. Любая будущая финансовая запись через бота требует отдельного подтверждения.
- Не устанавливать настоящий webhook и не отправлять реальные сообщения без прямого разрешения владельца.

## Git и окружения
- Основная рабочая ветка реализации Google Apps Script: audit/backend-upsert-guards. Перед работой всегда проверять текущий HEAD и Git status.
- Новые изменения выполнять в feature-ветках или в явно согласованной рабочей ветке; не переписывать чужие изменения.
- Не делать force-push, reset, удаление веток и массовую историю Git без согласования.
- Не менять main, не сливать PR и не менять default branch без отдельного прямого разрешения.
- Не публиковать секреты в коммиты, issue, PR, логи или чаты.
- Тестировать на вымышленных данных и отдельной тестовой таблице.
- Не менять настоящую семейную таблицу и реальные финансы в ходе тестов.
- Не менять Production Vercel settings/env vars и не выполнять Production deployment.
- Preview можно использовать для проверки, если он не связан с реальными финансовыми данными.
- Не публиковать Apps Script.

## Качество и отчётность
- Для каждого исправленного дефекта добавлять регрессионный тест.
- Минимальные проверки: typecheck/build, тесты балансов, Apps Script syntax, Apps Script API tests, git diff --check.
- Записывать только реально выполненные проверки и реальные результаты.
- Не утверждать, что Preview, Apps Script deployment или Telegram webhook работают, пока это не проверено.
- Предпочитать небольшие логические коммиты и один понятный PR на связанный этап.
- В отчёте указывать изменённые файлы, SHA, тесты, фактические результаты и оставшиеся риски.
